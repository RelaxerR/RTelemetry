## 2. Поток участника

```text
Сайт:  заявка (#23) → согласие на исследование (#17, версия документа) → код в ЛК (#35)
Игра:  «Участвовать в исследовании» → ввод кода → POST <сайт>/api/research/links
         {participantCode, installId, appVersion, contentVersion}
       200 → экран-подтверждение → SetConsent(Granted) → Track("study.enrolled")
       ошибка/офлайн → согласие не меняется, телеметрия не пишется, можно повторить
Сервер RTelemetry: принимает события установки; о коде не знает
Сайт (#38): ответы анкет + связки code ↔ installId → сопоставление с CSV RTelemetry по installId
```

### 2.1. Правила согласия в игре [решение автора, 2026-10-20]

- По умолчанию `ConsentState.Unknown`. До `Granted` клиент не пишет событий ни в память, ни на
  диск (инвариант RTelemetry, распространяется и на автоматические `ui.click`/`ui.miss`).
- `Granted` ставится **только** после успешного ответа API связки. Сбор у игроков без кода не
  ведётся: это вариант B из [privacy.md](privacy.md). Возрастной порог и процедура участия
  ещё ожидают ответа руководителей; ограничение 18+ не считается утверждённым.
- Вызов API связки — не телеметрия: его инициирует сам участник вводом кода. `installId`
  существует до согласия (`ITelemetryClient.InstallId`) и передаётся только сайту.
- Код участника хранится на устройстве (только для показа в настройках «Вы участник: XXXX…»)
  и в события RTelemetry не попадает (раздел 3).
- При запуске и возврате из фона игра проверяет статус исследовательской связки на сайте.
  До подтверждения `active` новые события не собираются и очередь не отправляется, включая
  автоматические события lifecycle и ввода. Сетевой сбой не означает отзыв согласия;
  отправка остаётся приостановленной до успешной проверки. Семидневный офлайн лицензии
  не разрешает офлайн-сбор исследовательских событий. Это требование к адаптеру игры;
  наличие такой блокировки в текущем SDK не подтверждено.

### 2.2. Отзыв согласия

| Где | Что происходит | Статус |
|---|---|---|
| В игре: «Выйти из исследования» | `SetConsent(Denied)` (стирает неотправленную очередь и отменяет запрос) → `ResetInstallId()` → удалить код с устройства. Текст: «уже отправленные данные удаляются в личном кабинете» | [решение автора, 2026-10-20] |
| На сайте (#25) | связки помечаются `revokedAt`, сайт вызывает `DELETE /v1/admin/installs/{installId}` в RTelemetry с admin key, пишет аудит, при ошибке повторяет | [сайт] |
| Сайт → игра | При запуске и возврате из фона — `GET <сайт>/api/research/links/{installId}` (`active` / `revoked` / `unknown`, без кода); до `active` действует блокировка из 2.1. При `revoked` — как «Выйти из исследования»; при `unknown` нужна повторная связка. События, пришедшие между отзывом и проверкой, сайт удаляет повторным `DELETE`; график повторов определяет сайт | [решение автора, 2026-10-20]; API и повторы — реализация сайта |
| Бэкапы БД телеметрии (#34, #12) | `DELETE` не чистит бэкапы: в политике (#17) указать срок ротации бэкапов как срок фактического удаления | [решает сайт] |

## 3. Событие `study.enrolled` [решение автора, 2026-10-20]

Пишется один раз сразу после `SetConsent(Granted)` по результату успешной связки. Имя
соответствует правилам конверта (`[a-z0-9._-]`).

Код участника в событие не передаётся. Связь `participantCode ↔ installId` хранится на сайте.

| Свойство | Тип | Значение |
|---|---|---|
| `consent_version` | string | Версия документа согласия на исследование с сайта (#17); игра берёт её из ответа API связки (см. 4.2) |
| `link` | string | `site` — связка создана через API сайта |

Бэкапы сайта (#12) обеспечивают восстановление связки; копия кода в RTelemetry не создаётся.

## 4. Код участника

### 4.1. Формат [решение автора, 2026-10-20; генерирует сайт]

8 случайных символов Crockford base32 (40 бит) + 1 контрольный, показ группами `XXXX-XXXX-X`.
Игра проверяет опечатки до запроса; сайт ограничивает перебор и возвращает одинаковую ошибку
для отсутствующего и отозванного кода. Контрольный символ не увеличивает случайность кода.

Контрольный символ — Luhn mod N для алфавита Crockford из 32 символов (`0-9`, `A-Z` без `I L O U`),
а не стандартный check symbol Crockford: тот добавляет `* ~ $ = U`, неудобные для ввода.

Нормализация ввода в игре и на сайте одинаковая: верхний регистр, удалить пробелы и дефисы,
`I`/`L` → `1`, `O` → `0`. Длина после нормализации — 9. Общие проверочные примеры
контрольной суммы нужно добавить при реализации в игре и согласовать с сессией сайта.

### 4.2. API связки [сайт] + дополнения [предложение]

Описано в #35 (`docs/research-api.md` сайта). Требования игры:

- Запрос: `POST /api/research/links`, ключ клиента в заголовке (как ключ проекта RTelemetry —
  не секрет, хранится в конфигурации сборки, не в git), тело
  `{ "participantCode", "installId", "appVersion", "contentVersion" }` (форматы — раздел 5).
- Ответ 200 (дополнение): `{ "status": "active", "consentVersion": "<версия документа>" }`.
  Игре нужна `consentVersion` для `study.enrolled`; без неё версия согласия в данных ВКР
  берётся только из БД сайта.
- Ответ на несуществующий или отозванный код — одинаковый (#35), например 404 с общим текстом;
  на лимит — 429. Игра показывает «код не принят» и не меняет согласие.
- Повторная связка той же пары `(code, installId)` идемпотентна; у кода может быть несколько установок [сайт].
- Статус установки для отзыва: `GET /api/research/links/{installId}` (раздел 2.2).

## 5. Версии сборки и контента [решение автора, 2026-10-20]

### 5.1. Сборка

| Поле | Формат | Откуда |
|---|---|---|
| `version` | SemVer `X.Y.Z` | `ApplicationDisplayVersion` в `Game.csproj` (меняется вручную или из тега) |
| `build` | целое, растёт монотонно, общее для всех платформ одного прогона CI | `ApplicationVersion` = номер прогона CI (`-p:ApplicationVersion=$GITHUB_RUN_NUMBER`); это же Android `versionCode` и iOS `CFBundleVersion` |
| `commit` | 40 hex | `GITHUB_SHA`, в сборку — через `-p:SourceRevisionId` (попадает в `InformationalVersion`) |
| `appVersion` в событиях | `{version}+{build}.{commit7}`, например `1.0.0+57.1a2b3c4` | игра переопределяет `o.AppVersion` в `UseRTelemetry` (это допускается [integration.md](integration.md)); лимит конверта — 64 символа |

Для беты используется ветка версий `0.x`; конкретный первый номер ещё не выбран.
Примеры `1.0.0` ниже и в таблице описывают синтаксис, а не утверждённый номер беты.

Сейчас (проверено 2026-10-20) `Game.csproj` жёстко задаёт `1.0.0` / `1`, а RTelemetry.Maui по
умолчанию пишет `VersionString+BuildString`, то есть все сборки пришли бы как `1.0.0+1`.
Локальные сборки без CI: `build = 0`, суффикс `.dev` (`1.0.0+0.dev`). На сайт они не публикуются,
а в анализе исключаются.

Сайт разбирает `appVersion` так: до `+` — `version`, до первой `.` после `+` — `build`, остаток —
коммит. Ключ релиза на сайте `(product, version, build, platform)` [сайт, #32] совпадает с этими полями.

### 5.2. Контент

Редактор при экспорте пишет манифест контента. Это изменение формата экспорта, поэтому по
правилам TheBookGame оно делается вместе: игра + редактор + тест + `docs/contract/`. Место файла
в экспорте определит это изменение.

```json
{
  "storyId": "tbg",
  "contentHash": "3fa2c1d09b7e…(sha256, 64 hex)",
  "storyCommit": "5816d84…(40 hex или null, если папка истории не git)",
  "storyDirty": false,
  "exportedAtUtc": "2026-10-20T12:00:00Z",
  "exporter": "StoryMakerIDE 1.0+1"
}
```

- `contentHash` — sha256 по отсортированным относительным путям и байтам семи папок контента,
  без самого манифеста; `exportedAtUtc` в хэш не входит.
- `contentVersion` = `{storyId}-{contentHash[0..12]}`, например `tbg-3fa2c1d09b7e`.
- Хэш выбран вместо коммита истории [решение автора, 2026-10-20]: из одного коммита возможны разные экспорты
  (грязное дерево, другая версия редактора), а `events.md` требует, чтобы два разных экспорта не
  имели одну версию. Коммит истории остаётся в манифесте и в описании релиза.
- Игра читает манифест встроенной истории при старте и передаёт его в `SetContentVersion`. Для
  пользовательской истории (только десктоп, Debug) берётся её манифест, при отсутствии —
  `custom-unknown`. Такие события исключаются из анализа.

по умолчанию создаётся черновик [сайт].

| Поле | Пример | Откуда берёт CI |
|---|---|---|
| `product` | `tbg` | константа workflow |
| `version` | `1.0.0` | `ApplicationDisplayVersion` |

| `contentVersion` | `tbg-3fa2c1d09b7e` | манифест контента из `Game/Resources/Raw` |

| `artifact.sizeBytes`, `artifact.sha256` | — | вычисляются в CI |

- `macos-catalyst-zip` — zip с `.app` без нотаризации; инструкцию по открытию даёт #29.
- Анкеты (#36) берут `appVersion` и `contentVersion` из записи релиза, поэтому оба поля обязательны.
- Ключ публикации — секрет GitHub Actions, в репозиторий не попадает.

## 7. Стабильные id сцен и выборов

### 7.1. Состояние (проверено 2026-10-20)

- `ExportIdRegistry` выдаёт новый `Guid.NewGuid()` каждой сцене и ресурсу при **каждом**
  экспорте. `Seed` используется только в тестах. Сохраняется лишь `start`.
- В источнике истории (`Parts/*.json`) у сцены есть стабильное поле `id` (в истории TBG оно
  сейчас равно имени сцены; новые сцены редактора получают GUID).
- Следствие для телеметрии: `scene_id` одной и той же сцены разный в каждой версии контента,
  поэтому охват сцен и выборов нельзя сравнить между итерациями ВКР. Сохранения прошлых
  экспортов отклоняются (TheBookGame#499).

### 7.2. Предложение (выполняется в TheBookGame, контракт — там)

- Экспортный id = `a{UUIDv5(namespace, "{область}:{ключ источника}")}a` в нынешнем написании
  (`_` вместо `-`). Формат файлов не меняется, меняется только детерминированность. Ключ сцены —
  `id` из источника, ключ ресурса — его имя.
- Проверить: сохраняет ли переименование сцены в редакторе её `id`. Если нет — переименование
  меняет `scene_id`, и это нужно записать как правило.
- Разовая смена всех id: сделать **до первой тестовой сборки**. Старые сохранения отклоняются
  существующим сообщением о другой версии.

### 7.3. Идентификаторы в событиях профиля `tbg` (уточнение [events.md](events.md))

| Свойство | Значение |
|---|---|
| `scene_id` | экспортный id контекста (`start` для стартовой сцены) |
| `choice_id` | `{scene_id}.c{n}`, где `n` — номер окна выбора в тексте сцены с 1 (окно — соседние строки `-Choice`) |
| `option_index` | позиция варианта в окне среди **всех** строк, с 1 (скрытые условием тоже считаются) |
| `option_id` | экспортный id целевой сцены (`-NextScene`) |
| `choice.shown` → видимые варианты | предлагается `visible` = `option_index` через запятую (`1,2,5`) вместо `option_ids`: при id из 38 символов семь вариантов уже не помещаются в 256 символов строки конверта |

Детали 7.2–7.3 остаются предложением реализации №2–3. `choice_id` с порядковым номером
окна не гарантирует сопоставимость после вставки нового окна; `option_id` по целевой сцене
не различает два варианта с одной целью. До реализации это нужно проверить на исходнике
и зафиксировать ограничения в контракте TheBookGame. Цель стабильных id утверждена,
но точный алгоритм ещё не считается решением автора.

Для анализа ВКР нужна карта «id → глава, имя сцены, окна выбора». Предложение: CI собирает её из
источника истории как артефакт релиза (`content-map.json`, ключ — `contentVersion`). В пакет
игры она не входит.

## 8. Срок хранения и выгрузка для ВКР

[сайт]: RTelemetry хранит сырые события 90 дней по `receivedAtUtc`; очистка при старте и каждые
6 часов; `RetentionDays` общий для всех проектов сервера.

Выгрузка RTelemetry: `GET /?handler=Csv` за Basic; колонки
`project,id,installId,sessionId,sequence,name,timestampUtc,receivedAtUtc,appVersion,contentVersion,platform,props`.
Ограничения: период не больше 366 дней, не больше 100 000 событий за запрос (иначе 413 — делить
период). Фильтр периода — по времени приёма.

Правила [решение автора, 2026-10-20]:

1. Срок на сервере оставить 90 дней. Выгружать CSV RTelemetry и CSV сайта (#38) **в конце
   каждого раунда теста и не реже раза в 30 дней**, чтобы ни одно событие не дожило до очистки
   невыгруженным.
2. Сырые выгрузки хранятся только локально в `Thesis/research/data/raw/` (игнорируется git).
   В репозиторий ВКР попадают агрегаты и обезличенные наборы с описанием происхождения.
3. Сопоставление: CSV сайта даёт `participantCode ↔ installId` и ответы анкет; CSV RTelemetry
   соединяется по `installId` [сайт, #38]. Отозвавшие согласие исключаются по списку отозванных
   связок из выгрузки сайта, в том числе из уже сохранённых локальных копий.
4. Повышение `RetentionDays` не выбрано. Ответственный за выгрузки и срок хранения локальных

## 11. Ключ тестирования и независимость исследования

Решения автора: TheBookGame #513–#514, сайт #60–#66. Подписанный Ed25519-токен
с `kid`, `sub/iid/nbf/exp/cycleEnd`, офлайн до 7 дней, онлайн-продление/отзыв,
`serverTime` и защита от отката часов, одна активная установка на ключ. В TEST дополнительно
действует вшитый срок сборки; DEV и RELEASE имеют отдельные правила. Истечение не удаляет сохранения.

**[Решение автора, 2026-10-20]** Идентификатор установки лицензии (`iid` токена) и
`installId` RTelemetry генерируются независимо. Один не вычисляется из другого и не
передаётся в API другой подсистемы. Исследовательский API не использует ключ или токен
тестирования как идентификатор участника; запрос и журналы не должны создавать связку
«ключ ↔ код участника / installId RTelemetry». Требования к авторизации API необходимо
согласовать с сессией сайта до интеграции.

Утечки отслеживаются сервером сайта по скачиваниям и активациям. Ключ, токен,
`sub`, `iid` лицензии и аккаунт сайта не попадают в события, props и выгрузки RTelemetry.
Выход из исследования меняет только исследовательский `installId`, а не активную лицензию.
API и защита из этого раздела ещё не реализованы в игре.
