## 2. Поток участника

После активации лицензии игрок может добровольно согласиться на исследование или
продолжить игру без участия. Игра запрашивает допуск на сайте. Сайт проверяет текущую
версию согласия и выдаёт отдельный случайный `telemetryInstallId` только для активного участия.
Приложение привязывает этот UUID в SDK, открывает локальную очередь и пишет `study.enrolled`.

### 2.1. Запись и отправка

- Без подтверждённого согласия SDK не пишет события в память и на диск. Это относится
  к событиям игры, lifecycle и нативного ввода.
- Последний успешный ответ сайта об активном участии разрешает локальную запись до
  указанного `expiresAt`, максимум семь суток. После истечения локальная запись прекращается.
  SDK ограничивает возраст неотправленного события семью сутками. Очередь переживает
  перезапуск только для прежнего UUID. Фоновая пауза отменяет текущую проверку или отправку.
- При запуске и возврате в игру приложение перепроверяет участие. SDK выполняет свежую
  проверку сайта перед каждой пачкой и повторной попыткой. Временный сетевой сбой
  сохраняет допустимую очередь и не открывает сетевую отправку. Подтверждённый отказ
  закрывает допуск, отменяет отправку и очищает очередь.
- Сервер RTelemetry для проекта пилота отдельно подтверждает допуск каждого UUID на
  сайте при приёме пачки. Временная недоступность сайта откладывает приём.

### 2.2. Отзыв согласия

При отзыве из игры локальный сбор немедленно прекращается. SDK очищает очередь,
отменяет проверку и отправку. Игра повторяет серверный отзыв при временной ошибке.
Сайт блокирует дальнейший допуск и вызывает `DELETE /v1/admin/installs/{installId}`
с админ-ключом RTelemetry. Успешный ответ на отзыв означает, что RTelemetry подтвердил
удаление. При отзыве на сайте игра получает новое состояние при следующей проверке.

RTelemetry сохраняет маркер удаления UUID. Это блокирует поздние пачки, включая
запрос, прошедший сетевую проверку до отзыва. Новое согласие получает новый UUID.
Политика ротации бэкапов определяет срок удаления резервных копий.

## 4. API допуска

Игра вызывает `POST /api/research/enrollment` с JSON
`{ token, installId, appVersion, contentVersion, action?, consentVersion?, telemetryInstallId? }`.
`installId` в запросе — UUID установки лицензии. `consentVersion` — целое число.
Действия — `status`, `grant`, `withdraw`. При повторе отзыва игра может передать UUID старой
связки в `telemetryInstallId`.

Ответ 200 содержит `status` (`active`, `inactive`, `revoked`) и `serverTime` в UTC.
Для `active` также возвращаются `consentVersion`, случайный `telemetryInstallId`
и исключительная UTC-граница `expiresAt`. При удалении в процессе статус уже показывает
`revoked`, а сам запрос отзыва возвращает 503 до подтверждения удаления. Ответ 409
сообщает об устаревшей версии согласия и содержит текущую версию, 403 означает отказ
в доступе, 400 — некорректный запрос, 503 — временную недоступность.

Сервер RTelemetry перед приёмом пачки проекта пилота вызывает `POST /api/research/authorization`
с JSON `{ telemetryInstallId }` и заголовком `X-Research-Authorization-Key`.
Сайт отвечает 204 при действующем участии и 403 при отказе. Неожиданные ответы и сетевые
ошибки трактуются как временная недоступность. Настройки подключения описаны в [server.md](server.md).

## 5. Версии сборки и контента [решение автора, 2026-10-20]

### 5.1. Сборка

| Поле | Формат | Откуда |
|---|---|---|
| `version` | SemVer `X.Y.Z` | `ApplicationDisplayVersion` в `Game.csproj` (меняется вручную или из тега) |
| `build` | целое, растёт монотонно, общее для всех платформ одного прогона CI | `ApplicationVersion` = номер прогона CI (`-p:ApplicationVersion=$GITHUB_RUN_NUMBER`); это же Android `versionCode` и iOS `CFBundleVersion` |
| `commit` | 40 hex | `GITHUB_SHA`, в сборку — через `-p:SourceRevisionId` (попадает в `InformationalVersion`) |
| `appVersion` в событиях | `{version}+{build}.{commit7}`, например `1.0.0+57.1a2b3c4` | игра переопределяет `o.AppVersion` в `UseRTelemetry` (это допускается [integration.md](integration.md)); лимит конверта — 64 символа |

Для первой беты автор подтвердил **0.1.0**; ветка версий — `0.x`.
Примеры `1.0.0` ниже и в таблице описывают синтаксис, а не утверждённый номер беты.

До TheBookGame #517 `Game.csproj` жёстко задавал `1.0.0` / `1`; RTelemetry.Maui по
умолчанию пишет `VersionString+BuildString`, поэтому все сборки пришли бы как `1.0.0+1`.
В #517 добавлены версия 0.1.0, метаданные коммита/номера и `AppBuildIdentity` в DI игры.
Переопределение `o.AppVersion` реализовано в адаптере TheBookGame #522.
Локальные сборки без CI: логический `TbgBuildNumber = 0`, суффикс `.dev` (`0.1.0+0.dev`).
Платформенный `ApplicationVersion` для локального пакета — 1, поскольку Android не принимает 0.
У публикуемой сборки оба номера совпадают. Локальные сборки на сайт не публикуются и из анализа исключаются.

Сайт разбирает `appVersion` так: до `+` — `version`, до первой `.` после `+` — `build`, остаток —
коммит. Ключ релиза на сайте `(product, version, build, platform)` [сайт, #32] совпадает с этими полями.

### 5.2. Контент

Редактор при экспорте пишет манифест контента. Это изменение формата экспорта, поэтому по
правилам TheBookGame оно делается вместе: игра + редактор + тест + `docs/contract/`.
В TheBookGame #517 выбран корневой файл `content-manifest.json`; код записи и чтения реализован.

```json
{
  "storyId": "tbg",
  "contentHash": "3fa2c1d09b7e…(sha256, 64 hex)",
  "storyCommit": "5816d84…(40 hex или null, если папка истории не git)",
  "storyDirty": false,
  "exportedAtUtc": "2026-10-20T12:00:00Z",
  "exporter": "StoryMakerIDE 1.0+1"
}
```

- `contentHash` — sha256 по отсортированным относительным путям и байтам принадлежащего
  экспорту контента (шесть папок + Settings/character_settings.json), без манифеста и чужих
  файлов; `exportedAtUtc` в хэш не входит. Точные префиксы длин и порядок байтов закреплены
  [в контракте TheBookGame](../../TheBookGame/docs/contract/script-format.md).
- `contentVersion` = `{storyId}-{contentHash[0..12]}`, например `tbg-3fa2c1d09b7e`.
- Хэш выбран вместо коммита истории [решение автора, 2026-10-20]: из одного коммита возможны разные экспорты
  (грязное дерево, другая версия редактора), а `events.md` требует, чтобы два разных экспорта не
  имели одну версию. Коммит истории остаётся в манифесте и в описании релиза.
- Игра читает манифест встроенной истории при старте и передаёт его в `SetContentVersion`. Для
  пользовательской истории (только десктоп, Debug) берётся её манифест, при отсутствии —
  `custom-unknown`. Такие события исключаются из анализа.

## 7. Стабильные id сцен и выборов

### 7.1. Исходное состояние до PR TheBookGame #516 (2026-10-20)

- `ExportIdRegistry` выдаёт новый `Guid.NewGuid()` каждой сцене и ресурсу при **каждом**
  экспорте. `Seed` используется только в тестах. Сохраняется лишь `start`.
- В источнике истории (`Parts/*.json`) у сцены есть стабильное поле `id` (в истории TBG оно
  сейчас равно имени сцены; новые сцены редактора получают GUID).
- Следствие для телеметрии: `scene_id` одной и той же сцены разный в каждой версии контента,
  поэтому охват сцен и выборов нельзя сравнить между итерациями ВКР. Сохранения прошлых
  экспортов отклоняются (TheBookGame#499).

### 7.2. Реализация TheBookGame #516

- Экспортный id вычисляется из SHA256 области и ключа исходника, первые 16 байт в прежнем
  формате `a<guid_с_подчёркиваниями>a`. Точный алгоритм и контрольные примеры закреплены
  [в контракте TheBookGame](../../TheBookGame/docs/contract/script-format.md).
- Ключ сцены — сохраняемый исходный `id`; переименование и перенос между главами его сохраняют.
  Ключ ресурса — имя файла. Дубликаты имён и исходных id сцен блокируют экспорт.
- Это технический выбор реализации, а не отдельное решение автора о UUIDv5. Встроенный пакет
  пока не переэкспортирован: разовая смена его id и проверка старых сохранений — до выдачи тестерам.

### 7.3. Идентификаторы в событиях профиля `tbg` (уточнение [events.md](events.md))

| Свойство | Значение |
|---|---|
| `scene_id` | экспортный id контекста (`start` для стартовой сцены) |
| `choice_id` | `{scene_id}.c{n}`, где `n` — номер окна выбора в тексте сцены с 1 (окно — соседние строки `-Choice`) |
| `option_index` | позиция варианта в окне среди **всех** строк, с 1 (скрытые условием тоже считаются) |
| `option_id` | экспортный id целевой сцены (`-NextScene`) |
| `choice.shown` → видимые варианты | реализовано `visible` = `option_index` через запятую (`1,2,5`) вместо `option_ids`: при id из 38 символов семь вариантов уже не помещаются в 256 символов строки конверта |

Детали 7.3 реализованы в TheBookGame #522 как технический выбор адаптера.
`choice_id` с порядковым номером окна не гарантирует сопоставимость после вставки окна;
`option_id` по целевой сцене не различает варианты с одной целью — нужен `option_index`.
Сравнение учитывает contentVersion. Источник scene_id — TextId, не изменяемый id сохранения.
По решению Славы пишутся сцены, выборы и финал по -End (сейчас конец главы 3), без line.shown.
Единственный автоматический вариант не считается выбором. latency_ms включает фон;
итоги duration_ms/choices_made оставлены null до выбора методики расчёта по выгрузке.
Подробности — docs/game/telemetry.md репозитория игры и [events.md](events.md).

Для анализа ВКР нужна карта «id → глава, имя сцены, окна выбора». Предложение: CI собирает её из
источника истории как артефакт релиза (`content-map.json`, ключ — `contentVersion`). В пакет
игры она не входит.

## 8. Срок хранения и выгрузка для ВКР

[сайт]: RTelemetry хранит сырые события 90 дней по `receivedAtUtc`; очистка при старте и каждые
6 часов; `RetentionDays` общий для всех проектов сервера.

Выгрузка RTelemetry: `GET /?handler=Csv` за Basic; колонки
`project,id,installId,sessionId,sequence,name,timestampUtc,receivedAtUtc,appVersion,contentVersion,platform,props`.
Ограничения: период не больше 366 дней, не больше 100 000 событий за запрос (иначе 413 — делить
период). Фильтр периода — по времени приёма.

Правила [решение автора, 2026-10-20]:

1. Ответственный за выгрузки — Слава. Срок на сервере оставить 90 дней. Выгружать CSV RTelemetry и CSV сайта (#38) **в конце
   каждого раунда теста и не реже раза в 30 дней**, чтобы ни одно событие не дожило до очистки
   невыгруженным.
2. Сырые выгрузки хранятся только локально в `Thesis/research/data/raw/` (игнорируется git).
   В репозиторий ВКР попадают агрегаты и обезличенные наборы с описанием происхождения.
3. Сопоставление CSV сайта и RTelemetry выполняется по UUID исследования `installId` [сайт, #38]. Отозвавшие согласие исключаются по списку отозванных
   связок из выгрузки сайта, в том числе из уже сохранённых локальных копий.
4. Повышение `RetentionDays` не выбрано. Срок хранения локальных

### 11.2. Независимость идентификаторов

Идентификатор установки лицензии (`iid` токена) и `telemetryInstallId` создаются независимо.
Игра отправляет лицензионный токен и UUID установки лицензии только сайту для проверки
допуска. Сайт выдаёт отдельный случайный UUID для конверта RTelemetry. Токен, ключ лицензии,
`sub`, `iid` и данные аккаунта сайта не попадают в транспорт, события или выгрузки RTelemetry.
Отзыв согласия останавливает исследование и удаляет его данные. Лицензия продолжает
действовать по собственным правилам.
